# API Event Bus Design

OpenVLP uses an in-process domain event bus inside the API service to publish
important domain changes and authentication events. The first subscriber is the
audit logger, but the event system is intentionally generic so other handlers
can be added without coupling domain services to logging, notifications, or
future integrations.

This document describes the event system concept and conventions. It is not an
endpoint reference.

## Goals

- Keep event publishing explicit at domain service boundaries.
- Give each event subject its own payload type.
- Keep services independent from the concrete event bus implementation.
- Preserve request correlation and actor information where an event originates
  from an HTTP request.
- Support namespace subscribers such as `auth.*` and `asset.*`.
- Keep audit logging structured and redact sensitive fields before writing
  logs.
- Stay in-process for now; this is not a durable queue or outbox.

## Main Components

The event system is split across generic bus code, domain event definitions,
service emitters, route context helpers, and event handlers.

- `apps/api/src/lib/eventbus/eventbus.ts` contains the generic async event bus.
- `apps/api/src/lib/eventbus/events/index.ts` defines the common domain event
  shape and combines all event payload maps.
- `apps/api/src/lib/eventbus/events/*.ts` defines per-domain event payloads,
  for example auth, user, asset, finding, role, and vulnerability events.
- `apps/api/src/lib/request-event-context.ts` extracts request-scoped event
  context from Hono.
- Domain services receive only the central `DomainEventEmitter` interface, then
  create a source-bound emit helper with `createDomainEventEmitter`.
- `apps/api/src/event-handler/index.ts` is the registration point for event
  handlers.
- `apps/api/src/event-handler/audit-logger.ts` registers the audit logger
  subscriber.

The application container creates one `EventBus<DomainEvent>` and passes it to
services as a `DomainEventEmitter`. This preserves hexagonal boundaries:
services can emit domain events without knowing how listeners are registered or
executed.

## Event Shape

Every domain event uses `DomainEventPayloadBase`:

```ts
{
  id: string
  correlationId?: string
  actor?: string
  source: string
  subject: string
  time: Date
  data: object
}
```

The fields have these meanings:

- `id`: unique event id. Generated by `createEventPayload` when omitted.
- `correlationId`: request id or other operation id used to connect logs.
- `actor`: user profile id of the user who caused the event, when known.
- `source`: module or service that emitted the event, such as `auth` or
  `asset`.
- `subject`: event name, such as `auth.success` or `asset.updated`.
- `time`: event creation time. Generated by `createEventPayload` when omitted.
- `data`: subject-specific payload.

The `subject` stays on the event even though listeners also receive events
through subject subscriptions. It is used for type narrowing, logging, wildcard
matching, and generic handler code.

## Event Subjects And Payloads

Event payloads are defined as maps from event subject to payload shape. Each
domain owns its own file:

- `events/auth.ts`
- `events/user.ts`
- `events/asset.ts`
- `events/finding.ts`
- `events/role.ts`
- `events/vulnerability.ts`

`events/index.ts` combines these maps into `EventPayloads`. From that map the
code derives:

- `EventSubject`: all known event subjects.
- `DomainEvent`: the discriminated union of all domain events.
- `DomainEventFor<TSubject>`: the concrete event type for one subject.

This gives each event name a different `data` type while still allowing one
shared bus:

```ts
emitAssetEvent(
  "asset.updated",
  { previous, current },
  eventContext
)
```

The payload above is valid only for `asset.updated`. A payload for another
subject, for example `{ asset }`, would be rejected by TypeScript.

## Emitting Events

Services should not call `createEventPayload` directly for normal domain
events. They should create a source-bound helper once and use it for the
service's supported subject namespace:

```ts
const emitAssetEvent = createDomainEventEmitter<AssetEventSubject>(
  domainEventEmitter,
  "asset"
)

emitAssetEvent("asset.created", { asset }, eventContext)
```

`createDomainEventEmitter` handles the common event envelope:

- assigns `source`
- copies `actor` and `correlationId`
- creates the event id
- creates the event timestamp
- sends the event to the injected `DomainEventEmitter`

The helper currently fire-and-forgets the underlying async `emit` call. Domain
service writes must not depend on listener side effects to be correct.

## Request Context

HTTP routes convert Hono context into `DomainEventContext` with
`requestEventContext`:

```ts
const eventContext = requestEventContext(c)
```

The helper currently maps:

- `actor` from `c.get("user")?.id`
- `correlationId` from `c.get("requestId")`

Routes pass this context into service methods that can emit events. Services do
not read Hono context directly.

Auth routes have a smaller correlation-only path for unauthenticated actions
such as login attempts, where there may be no actor yet.

## Subscribing To Events

Listeners are registered against the concrete `EventBus<DomainEvent>`. The bus
supports:

- exact subjects, for example `user.created`
- namespace wildcards, for example `user.*`
- the global wildcard `*`

Wildcard matching is namespace based. `user.*` matches `user.created` and
`user.profile.updated`, but not the bare subject `user`.

Listeners run sequentially in registration order. If a listener throws or
rejects, the bus forwards the failure to the configured error handler and then
continues with later listeners. `emit` does not reject because of listener
failures.

New application handlers should be registered from
`apps/api/src/event-handler/index.ts`. Domain services should not import
handlers directly.

## Audit Logging

The audit logger is the first subscriber. It registers namespace listeners for:

- `asset.*`
- `auth.*`
- `role.*`
- `user.*`
- `finding.*`
- `vulnerability.*`

The audit log message is the event subject. The structured log fields include:

- event id
- event subject
- event source
- event time
- actor
- correlation id
- redacted event data

`auth.failure` is logged at `warn`; other audited events are logged at `info`.

Audit serialization redacts sensitive property names anywhere in event `data`.
The current redaction list includes:

- `sessionId`
- `passwordHash`
- `evidence`

Redaction is a guardrail, not permission to emit secrets. Event payloads should
still prefer public or domain-safe shapes, for example `UserProfile` instead of
internal user records that include `passwordHash`.

## Current Event Families

The API currently emits these event families:

- Auth: login success, login/session failures, session creation, and session
  revocation.
- User profiles: created, updated, and deleted.
- Assets: created, updated, and deleted, using `AssetWithCustomFields` so asset
  custom field assignments and values are included in asset lifecycle events.
- Findings: created, updated, and deleted.
- Vulnerabilities: created, deleted, and source mapping creation.
- Roles: updated and deleted.

Update events use `{ previous, current }` where practical. This gives audit
consumers a structured diff source without requiring them to reload historical
state.

## Payload Guidelines

Use these rules when adding or changing events:

- Add payload types in the domain-specific `events/*.ts` file.
- Export and combine the payload map through `events/index.ts`.
- Use public or domain-safe data shapes; do not emit internal records with
  secrets.
- Include enough data for an audit log or subscriber to understand what
  changed without issuing another read in the normal case.
- Prefer `{ previous, current }` for update events.
- Treat deletion events as facts about the deleted object; include the object as
  it existed before deletion where available.
- Keep event subjects stable. Renaming a subject is a breaking change for
  subscribers.
- Do not emit events for read-only queries.
- Do not make service correctness depend on listener side effects.

## Testing

Service tests should use `createDomainEventCollector` from
`apps/api/src/test/eventbus.ts`. It provides:

- `emitter`: a `DomainEventEmitter` test double
- `events`: collected event objects
- `subjects()`: emitted subject list
- `eventsFor(subject)`: typed filtering by subject
- `clear()`: reset between test steps

Tests that assert audit behavior should serialize events with
`serializeDomainEventForLog` or exercise the audit logger subscriber directly.
Security-sensitive tests should assert that secrets such as `passwordHash` and
`sessionId` are absent or redacted in emitted events and audit log fields.
