# Frontend Architecture

This project follows a feature-based architecture.
The primary goal is to keep business functionality cohesive while maintaining clear dependency boundaries.

## Project Structure

```text
src/
├── routes/                    # TanStack Router route definitions
├── features/                  # Business/domain features
│   ├── auth/
│   ├── assets/
│   ├── findings/
│   └── ...
├── components/                # Contains Domain-independent shared components
│   ├── ui/                    # shadcn/ui primitives
├── hooks/                     # Application-wide hooks
├── integrations/              # third-party framework wiring
├── lib/                       # Infrastructure and shared utilities
├── test/                      # Common testing utilities
├── routeTree.gen.ts           # Generated by TanStack Router
└── main.tsx
```

## Routes

`src/routes` represents the application's URL hierarchy.

Route files should remain thin and contain routing and composition concerns:

- route definitions
- path parameters
- validated URL/search parameters
- loaders that coordinate data preloading
- redirects and guards
- route-level pending and error boundaries

Routes own the URL contract, including parameter names, search-parameter validation, and navigation behavior.
Features may export reusable schemas or query definitions.
Routes still decide their URL representation and loading time.

Business logic, endpoint calls, cache policy, and substantial UI should live in the corresponding feature.

```tsx
import { createFileRoute } from "@tanstack/react-router";

import { AssetDetailsPage, assetDetailsQueryOptions } from "@/features/assets";

export const Route = createFileRoute("/assets/$assetId")({
  loader: ({ context: { queryClient }, params: { assetId } }) =>
    queryClient.ensureQueryData(assetDetailsQueryOptions(assetId)),
  component: AssetRoute,
});

function AssetRoute() {
  const { assetId } = Route.useParams();
  return <AssetDetailsPage assetId={assetId} />;
}
```

## Features

Each business domain lives under `src/features`.

```text
features/assets/
├── api/
├── components/
├── hooks/
├── pages/
├── queries/
├── schemas/
├── types.ts
└── index.ts
```

A feature should contain code that specifically belongs to that domain, including:

- domain-specific components
- API functions
- (Tanstack) queries and mutations
- state and hooks
- schemas and types
- feature-level pages

## State and Data Ownership

Use the state mechanism that owns the relevant lifecycle:

- TanStack Query owns server state.
- TanStack Router search parameters own shareable and navigational state.
- TanStack Form owns form state.
- React component state owns ephemeral UI state.
- A feature-owned provider may own genuinely application-wide client state that does not fit the categories above.

Do not mirror Query data or validated search parameters into React state or context.

Each feature owns its query keys, `queryOptions` factories, mutations, cache policy, and invalidation behavior.
The feature API layer owns endpoint calls; query functions call that layer rather than the generic API client directly.

Route loaders preload critical data with the feature's exported query options.
Pages read the same options with `useSuspenseQuery`, so routing and rendering share one cache entry and one data contract.
The application creates one Query client and makes it available to route loaders through router context.
Features must not create their own Query clients.

Public modules imported by loaders must be side-effect-free.
In particular, they must not perform network requests or initialize browser-only behavior at module scope.

## Contracts and Feature Types

`@exposurenexus/contracts` is the source of truth for shared domain models and API request and response contracts.

- Feature API and query modules import the relevant contract subpaths and must not redeclare transport schemas or types.
- Feature-local schemas and types describe UI concerns such as forms, search parameters, component props, and view models.
- A feature maps a transport model to a view model at its API/query seam when the UI needs a different shape.
- `lib`'s generic API client remains contract-agnostic and must not import feature code or domain-specific contracts.
- Contract-specific validation, decoding, and error interpretation stay in the owning feature.

## Feature Dependencies

Features may depend on other features only when the dependency is one-way and follows domain responsibility.
The feature dependency graph must remain acyclic.

Cross-feature consumers must use the target feature's public interface:

```tsx
import { AssetTable } from "@/features/assets";
```

Cross-feature deep imports are forbidden:

```tsx
// Forbidden
import { AssetTable } from "@/features/assets/components/asset-table";
```

Expose only supported dependencies through the feature's `index.ts`:

```ts
export { AssetTable } from "./components/asset-table";
export { assetDetailsQueryOptions } from "./queries/asset-details";
```

The public interface should remain small and intentional.
It must not re-export the entire feature implementation.
Code inside a feature imports its sibling modules directly and must not import through its own `index.ts`.

When a workflow coordinates peer features, compose them in a route or a higher-level workflow feature.
Do not make peer features depend on each other in both directions.

```text
Good:

finding-triage
 ├──> findings
 └──> assets

Forbidden:

findings ──> assets
    ^          │
    └──────────┘
```

Do not move domain-specific code into shared folders merely because multiple features use it.
Ownership is determined by domain responsibility, not usage count.

These constraints must be enforced in linting:

- reject cross-feature deep imports
- reject feature dependency cycles
- keep feature-internal imports distinct from imports through another feature's public interface

The current approved feature dependencies are:

| Feature                    | May import feature roots       |
| -------------------------- | ------------------------------ |
| auth, roles, custom-fields | none                           |
| users                      | roles                          |
| vulnerabilities            | users                          |
| assets                     | users, custom-fields           |
| findings                   | assets, users, vulnerabilities |
| dashboard                  | assets, findings               |

`apps/ui/.oxlintrc.json` enforces these boundaries for production, tests, and stories,
including dynamic imports. Cross-feature callers use `@/features/<name>`; feature
internals use direct implementation paths. Test and story overrides retain the same
feature dependencies while allowing test support imports. Production shared components
may use only `lib/utils` and `lib/format` as presentation-safe infrastructure.

When editing the restrictions, keep regex restrictions before glob allowlist exceptions:
Oxlint stops checking patterns when an import matches a negated glob. Every override of
`no-restricted-imports` must retain the relative-import and deleted API/context restrictions.
Cycle detection ignores type-only edges and external packages; self-imports are errors.

## Shared Components

### `components/ui`

Contains shadcn/ui primitives:

```text
components/ui/
├── button.tsx
├── dialog.tsx
├── input.tsx
└── table.tsx
```

These components should remain domain-independent.

### `components/`

Contains application-wide components that are not owned by a specific business feature.

For example:

```text
components/
├── data-table.tsx
├── error-state.tsx
└── page-header.tsx
```

A generic `DataTable` belongs here, while a `AssetTable` belongs in `features/assets`.

## Infrastructure

`src/lib` contains domain-independent application infrastructure and shared utilities.

Examples:

```text
lib/
├── api-client.ts
├── env.ts
├── query-client.ts
└── utils.ts
```

The generic API client handles transport concerns such as the base URL, request execution, and generic failures.
Concrete endpoint paths, contract validation, and domain-specific error handling belong to feature API modules.

`lib` must not import routes, features, components, or domain-specific contracts.
Asset, finding, authentication, or other business-specific logic must not be placed in `lib`.

## Dependency Direction

Dependencies point from an importing module to a module it may import.
Allowed dependencies are:

| Importing module  | May import                                                                                                                                           |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `main.tsx`        | generated route tree, integrations, shared components, and feature public interfaces needed for providers                                            |
| `routes`          | feature public interfaces, shared components and hooks, integrations, and domain-independent `lib` modules                                           |
| `features/<name>` | its own implementation, approved feature public interfaces, shared components and hooks, `lib`, `@exposurenexus/contracts`, and third-party packages |
| `components`      | `components/ui`, shared hooks, presentation-safe `lib` utilities, and third-party packages                                                           |
| `components/ui`   | other UI primitives, presentation-safe `lib` utilities, and third-party packages                                                                     |
| `hooks`           | domain-independent `lib` modules and third-party packages                                                                                            |
| `integrations`    | domain-independent `lib` modules and the integrated third-party packages                                                                             |
| `lib`             | domain-independent third-party packages only                                                                                                         |

An allowed dependency is not a requirement to introduce an abstraction or wrapper.
Domain-independent modules must never depend on routes or features.
Cross-feature dependencies are allowed only through explicit public interfaces and must form an acyclic graph.
